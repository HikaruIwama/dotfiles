# テストコードの規約

仕様に沿った振る舞いを守り、その振る舞いが壊れたら失敗するテストを作る。対象リポジトリの規約、既存のテスト構成、実行手順を優先し、使用中の言語とフレームワークに合わせる。

## 守る振る舞いと期待値を決める

- テストを書く前に、守る仕様と想定する壊れ方を整理する。期待値は仕様や受け入れ条件から導き、実装の出力をそのまま正解にしない。仕様が曖昧で合否が変わる場合は確認する。
- 公開された振る舞いを検証する。内部の呼び出し順序や補助関数の分割など、仕様に含まれない詳細を固定しない。
- 戻り値は、契約上の値、型、構造を検証する。オブジェクト全体が契約なら全体を比較し、配列は件数に加えて内容も確かめる。順序は仕様で意味を持つ場合に検証する。
- 部分一致や真偽値への変換で、契約上の欠落や型の違いを見逃さない。可変のメタデータなど契約外の要素まで固定して、正しい変更を妨げない。
- コールバックや外部への副作用は、契約に応じて引数と回数を確かめる。成功時のエラー通知や失敗時の書き込みなど、発生してはいけない処理も検証する。呼び出し自体が契約でない場合は、観測可能な結果を優先する。
- カバレッジは未検証箇所を探す手掛かりとして使う。数値を上げるためだけのテストや、実装の計算手順を複製して答え合わせするテストは追加しない。

## 不具合に合うテスト層とケースを選ぶ

対象の不具合を検出できる層の中から、実行が速く、失敗原因を特定しやすいものを選ぶ。

| 検証する振る舞い | 選ぶテスト |
| --- | --- |
| 計算、変換、分岐、状態遷移 | 単体テスト |
| 広い入力領域に共通する性質や不変条件 | プロパティベーステスト（PBT） |
| クエリ、DB制約、トランザクション、永続化 | 実際の対象DBを使う結合テスト |
| 外部APIとの接続や入出力の整合性 | 結合テスト、契約テスト |
| 画面をまたぐ主要フロー、実ブラウザ固有の操作や描画 | E2Eテスト |

- 正常系、異常系、境界値、状態遷移から、仕様に関係するケースを選ぶ。例えば上限がある処理では、上限の直前、一致、直後で期待する結果を確かめる。
- 入力の組み合わせが小さな有限集合なら全列挙を検討する。値域が広く、仕様から不変条件を定義できる場合はPBTを検討する。生成範囲と性質を明示し、失敗した入力やシードを再現できるようにする。PBTの成功を全入力に対する証明とは扱わない。
- 既存の型や生成処理で不正な値を排除している場合は、その入口で拒否を検証する。後続の処理では有効な値を使い、テストデータを作るために型安全性を回避しない。外部入力の実行時検証は型検査だけで代替しない。
- E2Eに細かな分岐や境界値を集約しない。探索的テストで発見した不具合も、原因を検出できる最小の層に回帰テストを追加する。

## 外部境界を制御して結果を安定させる

- 検証対象のロジックは本物を実行する。時刻、乱数、通信などの外部境界を、既存の注入手段やテストフレームワークの機能で制御する。
- 結合を検証するテストでは、その接続先をモックで置き換えない。例えばDB制約を確かめるテストでは、実際のスキーマを持つテスト用DBに書き込む。契約テストだけで実接続まで確認したとは扱わない。
- モック、タイマー、共有状態、テストデータは、失敗した場合も後処理で戻す。テスト同士を実行順序に依存させない。
- 非同期処理の完了を待ってから結果を検証する。固定時間の待機に頼らず、対象の完了通知や条件を期限付きで待つ。再試行で不安定な失敗を隠さない。

## 失敗すべきときに失敗するか確かめる

- 不具合修正では、追加する回帰テストが修正前に対象の不具合で失敗し、修正後に成功することを確認する。環境不足や構文エラーによる失敗を再現成功に数えない。修正前の確認ができなければ理由を報告する。
- 重要な検証や既存テストの置換では、代表的な誤りを一時的に入れるなどして検出力を確かめる。ミューテーションテストを使う場合も、対象を絞った隔離環境で実行し、意図的な誤りを成果物に残さない。
- E2Eなど既存テストを減らす場合は、守っていた主要な振る舞いを移行先で検出できることを確認してから置き換える。実ブラウザや接続環境に固有の検証は残す。
- 期待値やスナップショットは、意図した仕様変更を根拠に更新する。差分を確認せず一括更新したり、現在の実装に合わせて失敗を消したりしない。
- 対象テストから実行し、変更の影響範囲とリポジトリの手順に沿って関連テスト、型検査、Lintを実行する。確認できた振る舞い、実行結果、未検証の範囲と理由を報告する。

## 変更範囲を保つ

必要なテストは、それが守る実装変更と同じ変更単位に含める。本体の型設計、CI、依存ライブラリの変更を自動的に作業範囲へ含めない。PBTやミューテーションテストのツール導入は必須にせず、既存の手段で検証できるかを先に確認する。新しい依存が必要な場合は、対象環境の依存関係の規約に従う。
