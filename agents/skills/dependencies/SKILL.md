# 依存関係を追加するときの規約

リポジトリに依存関係の方針（許可ライセンスの一覧、利用可能なレジストリなど）がある場合は、そちらに従う。この規約は、依存の新規追加、別パッケージへの置き換え、メジャーバージョンの更新に適用する。開発用の依存（devDependenciesなど）にも同じ規約を適用する。

## 追加の要否を判断する

- 標準ライブラリ、既存の依存、数十行程度の自前実装で足りる場合は追加しない。
- 同じ用途の依存が既にある場合は、それを使う。

## 候補を確認する

### ライセンス

- 次の寛容型ライセンスは追加してよい：MIT、BSD-2-Clause、BSD-3-Clause、Apache-2.0、ISC、0BSD、Unlicense、CC0-1.0。
- 次の場合は、追加前に理由を示してユーザーに確認する。
  - コピーレフト（GPL、AGPL、LGPL、MPL、EPLなど）
  - ソース公開型・利用制限付き（SSPL、BSL、Elastic License、Commons Clauseなど）
  - ライセンスが不明、独自、またはレジストリの表記とリポジトリのLICENSEファイルが一致しない
- ライセンスはレジストリの表記とリポジトリのLICENSEファイルの両方で確かめる。
- 推移的依存のライセンスも、確認ツール（`license-checker`、`pip-licenses`、`cargo deny`など）が使える場合は確かめる。

### 保守状況と信頼性

- 最終リリース日、未対応Issueの状況、メンテナを確認する。長期間更新がない、またはアーカイブ済みの場合は報告する。
- パッケージ名を公式ドキュメントやリポジトリで確かめ、名前の似た偽パッケージ（typosquatting）を避ける。
- ダウンロード数や利用実績が極端に少ない場合は報告する。

### 脆弱性

- 追加するバージョンに既知の脆弱性がないか、`npm audit`、`pip-audit`、`cargo audit`、GitHub Advisory Databaseなどで確かめる。

## ユーザーに確認してから追加する

追加する前に、次の内容を提示してユーザーの承認を得る。

- パッケージ名とバージョン
- 追加する理由と、検討した代替手段（標準ライブラリ、既存の依存、自前実装）
- ライセンス
- 保守状況と脆弱性の確認結果、懸念点

## 追加の手順

- `package.json`などのマニフェストを手で編集せず、パッケージマネージャのコマンドで追加する。
- 実行時の依存と開発用の依存を区別する。
- lockfileを更新し、マニフェストと同じコミットに含める。
- バージョン指定の書き方（範囲指定か固定か）は、リポジトリの既存の書き方に合わせる。
