# NG表現と置き換え

すべて「NG → OK」の対で示す。理由がわからない場合は該当行の説明を読む。

## 冗長

| NG | OK | 理由 |
| --- | --- | --- |
| 〜することができる | 〜できる | 「ことができる」は「できる」の言い換えに過ぎない |
| 〜という形で | （削除する） | 指す内容を増やさない |
| 〜に関しまして | 〜について | 同じ意味をより長く言っているだけ |
| 実装を行う | 実装する | 「〜を行う」は動詞化できる場合は動詞にする |
| 確認を行う | 確認する | 同上 |
| 〜することが可能である | 〜できる | 同上 |
| 〜する必要がある（単なる行動の指示として） | 〜する | 主語が明確な指示なら、義務の言い回しを省いて言い切る |

## 曖昧語

具体的な動作、数値、条件が省略された語は、その場で埋める。

| NG | 問題 | OK |
| --- | --- | --- |
| 適切に処理する | 何をするか不明 | 3回まで再試行し、失敗したらSlackに通知する |
| 柔軟に対応する | 何をするか不明 | 設定ファイルで再試行回数を変更できるようにする |
| 基本的に問題ない | 例外の条件が不明 | 〇〇の場合を除き問題ない |
| 必要に応じて実施する | 実施の条件が不明 | エラー率が5%を超えた場合に実施する |
| 対応する／実施する／検討する（単独で結論として使う） | 誰が何をするか不明 | 担当者、作業内容、期限を明記する |
| 業界の専門家によると／調査結果が示すように（出典不明のまま） | 誰の・どの調査か不明で検証できない | 「〇〇社が公表した△△調査では」のように具体的に書く。出せないなら自分の見解と明記する |

## 責任がぼやける表現

| NG | 問題 | OK |
| --- | --- | --- |
| 対応が必要とされている | 誰が対応するか不明 | 〇〇チームが〇月〇日までに対応する |
| 修正が求められる | 誰が求めているか不明 | レビューで指摘された内容を〇〇が修正する |
| 〜させていただきます（多用） | 敬語の濫用 | 通常の敬体（〜します）で足りる場面が多い |
| 拝見させていただきました | 二重敬語 | 拝見しました |
| おっしゃられました | 二重敬語 | おっしゃいました |
| あまり推奨されません／注意が必要です（判断を求められる場面での結論として） | 言い切るべき場面で結論をぼかしている | 「非推奨」「〜しない」のように言い切る。手順書、ADR、レビュー指摘で特に |

無主語の受動態（「〜が必要とされている」「〜が求められる」）は、行為者を主語にした能動態に直す。行為者が本当に不明な場合は、不明であることを明記する（「原因は現時点で不明」）。

## LLMっぽい表現

内容を増やさずに「書いている感」だけを出す言い回し。使わない。

| NG | 分類 | OK |
| --- | --- | --- |
| 重要なのは〜である | 予告 | 主張をそのまま書く |
| 本ドキュメントでは〜について見ていく | 予告 | 結論を先に書く |
| 〜に他ならない | 空虚な言い切り | 主張の内容をそのまま書く |
| 多角的に分析すると | 空虚な形容 | 何をどう見たかを書く |
| 包括的に／総合的に | 空虚な形容 | 対象範囲を具体的に書く |
| 掘り下げる／深掘りする | 空虚な動詞 | 何をどう調べた・書いたかを書く |
| 〜という観点から／〜という側面から | 接続の型 | 新しい情報がなければ削る |
| さらに、また、加えて（の連打） | 接続の型 | 内容が並列でなければ削る。並列なら1つに絞る |
| 〜と言えるだろう（根拠なく主張を弱める場合） | 弱い緩和 | 根拠があれば断定する。なければ根拠を書く |
| 非常に／極めて／大いに | 空虚な強調 | 数値や具体的な程度で示す |
| 箇条書きの全項目を「**ラベル：**内容」の型で揃える | 定型フォーマット | ラベルを外し、内容を直接書く（用語を定義する箇条書きを除く） |
| 「Xではない。Yだ。」「単なるXではなく、Yだ。」 | 対比の空振り | Yだけを直接書く |
| データの直後に「〜を示しており」「〜を物語っている」と続けて意義付けする | 根拠のない意義付け | 事実と評価を分ける。評価を書くなら根拠になる数値・条件を示す |
| ケースバイケース／一概には言えません（文書の結論として） | 結論回避 | 判断を下す。下せない場合は、下せない理由を具体的に書く |
| 「専門用語は使わずに説明します」と冒頭に書く | 振る舞いの宣言 | 宣言を書かず、平易な言葉の説明をそのまま始める |
| 「△△の話題は本書では扱いません」と書く | 振る舞いの宣言 | 扱わない。判断は実行だけする |

悪い例：「本設計では、拡張性を重要な観点として多角的に検討を行った。」
良い例：「本設計では、プラグイン追加時に既存コードを変更しなくてよいことを条件にした。」

ヘッジ（「〜ことがある」「〜場合がある」「〜可能性がある」）は1段落に2つ以上重ねない。接続表現（「さらに」「また」「加えて」など）は同一段落で2回以上使ったら1つに絞る。

推量、可能性、仮定を表す「かもしれない」「〜だろう」は、根拠なく主張を弱めている場合だけ削る。未確認の事実、確度の低い推測を表す場合は残す（「事実と推測を分離する」という`SKILL.md`の規則を優先する）。

振る舞いの宣言（「〜します」「〜しません」という自分の振る舞いの宣言）は本文に書かない。制約の遵守は出力内容そのもので示す。判別基準：その文を消しても読み手が困らないならメタ発言である。「予告」も同じ構造である。例外：文書の内容として意味を持つ範囲記述（「本仕様の対象は〜である」など）は宣言ではなく仕様なので残す。判断に迷う場合は「この文を読み手が必要としているか」で決める。

## ビジネスジャーゴンの言い換え

カタカナの外来語で成立している言い回しは、和語・漢語に言い換えられないか確認する。API、デプロイ、リポジトリのように技術用語として定着している語はそのままでよい。

| NG | OK |
| --- | --- |
| 〜にレバレッジを効かせる | 〜を活用する |
| ソリューション | 解決策、仕組み |
| イノベーティブな | 新しい、独自の |
| 〜にコミットする | 〜を引き受ける、必ず〜する |
| 〜をアラインする | 〜を揃える、〜を合わせる |
| 〜にディープダイブする | 〜を詳しく調べる |
| 〜をスケールする | 〜を拡大する |
| 〜にピボットする | 〜に方針転換する |

カタカナ語が3語以上連続したら、和語に置き換えられないか疑う。
