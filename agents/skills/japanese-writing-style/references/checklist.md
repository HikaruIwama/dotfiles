# レビューチェックリスト

表記 → 文 → 段落 → 文書全体の順に、粒度を上げながら見る。指摘は「該当箇所の引用 → 何が問題か → 書き換え案」の3点セットで書く。

## 1. 機械的に検出できる項目（先にgrepで潰す）

人が読む前に、以下のパターンで一括検索して直す。ripgrepの例（活用形をまとめて拾うため、語幹の一部で検索する）：

```bash
rg '出来|下さい|する事|た事|事が|事は|様々|更に|及び' <対象ファイル>
rg 'ことができ|という形|を行|に関しまして' <対象ファイル>
rg '重要なのは|に他ならない|多角的|包括的|掘り下げる|深掘りする|という観点から|という側面から' <対象ファイル>
rg 'ケースバイケース|一概には言えません|業界の専門家によると|調査結果が示すように|を示しており|を物語っている' <対象ファイル>
rg '\*\*[^*]{1,20}[:：]\*\*' <対象ファイル>
rg '！|!|―|—|——|～' <対象ファイル>
rg 'させていただ|おっしゃられ' <対象ファイル>
rg 'レバレッジ|ソリューション|イノベーティブ|コミットする|アライン|ディープダイブ|スケールする|ピボット' <対象ファイル>
rg '非常に|極めて|大いに' <対象ファイル>
```

ヒットした行がコードフェンス内かどうかを確認し、コードブロックの中身は対象外にする。

ヒットした箇所は基本的に`references/orthography.md`・`references/ng-phrases.md`の対応する置き換えを適用する。ただし「事」を含むパターンは、「事件」「事故」「事業」「仕事」「大事」「工事」のような実質名詞の一部にもヒットする。形式名詞（〜する事、〜た事、〜という事が）かどうかを確認してから置き換える。

## 2. 表記（references/orthography.md）

- [ ] 形式名詞、補助動詞、接続詞、副詞がひらがなで書かれている（事→こと、出来る→できる、様々→さまざまなど）
- [ ] 送り仮名が統一されている（行う、問い合わせなど）
- [ ] 句読点・記号が既定どおりである（感嘆符を使っていない、ダッシュ類を使っていない、中黒は固有名詞の内部だけ）
- [ ] カタカナ語の長音が、チームの決定・用語統一表と一致している
- [ ] 英字と日本語の間、数字と日本語の間にスペースが入っていない
- [ ] 数字が半角で、4桁以上の数量に3桁ごとのカンマが入っている（年、番号、ID、コード値を除く）
- [ ] 日付・時刻が絶対表記になっている（相対表現が残っていない）
- [ ] 用語統一表にある語が、表のとおりに使われている

## 3. 文

- [ ] 一文で言っていることが一つである（「〜し、〜し、〜する」の長い連鎖を分割できないか確認する）
- [ ] 主語と述語の対応が取れている。無主語の受動態で責任がぼやけていない
- [ ] `references/ng-phrases.md`の冗長表現、曖昧語、LLMっぽい表現が残っていない
- [ ] 振る舞いの宣言（「〜します」「〜しません」のメタ発言）が混入していない
- [ ] 断定の強さが、本文中の根拠の強さと一致している（未確認のことを確定的に書いていない）
- [ ] 出典が具体的である（「専門家によると」「調査結果が示すように」で済ませていない）
- [ ] 結論を出すべき場面を「ケースバイケース」「一概には言えません」で済ませていない

## 4. 段落

- [ ] 段落の最初の文を読めば、その段落の主題がわかる
- [ ] 一つの段落に一つのトピックだけが置かれている
- [ ] 前の段落との関係が、接続表現か文脈で明示されている
- [ ] 箇条書きが並列の項目にだけ使われている（因果・論証を箇条書きに分解していない）

## 5. 文書全体

- [ ] 短い導入（目的・対象の1〜2文）の直後、最初の実質的な節の冒頭で結論・要点がわかる。導入や背景だけがだらだら続いていない
- [ ] 見出しだけを並べて読んでも、文書の流れがわかる
- [ ] 見出しが内容を特定できる句になっている（「概要」「その他」だけで済ませていない）
- [ ] 前方参照（「後述する」「詳細は〇〇を参照」）が実際に回収されている
- [ ] コードブロック、ログ、引用、固有名詞、製品名の正式表記が変更されていない

## 文書種別ごとの追加チェック

### 障害報告

- [ ] 時系列が発生順に並んでいる
- [ ] 事実（ログ・計測値）と推測が、文として分離されている
- [ ] 恒久対応の担当者と期限が明記されている

### ADR・設計書

- [ ] 決定した内容が、短い導入の直後（最初の実質的な節の冒頭）にある
- [ ] 決定の理由が書かれている
- [ ] 検討して却下した案が、却下理由とともに書かれている

### PR・Issueの説明

- [ ] 変更点が箇条書きまたは1段落で明確である
- [ ] 動作確認の方法が書かれている
- [ ] 影響範囲（互換性、既存機能への影響）が書かれている

### 手順書

- [ ] 操作指示が常体の終止形（「保存する」「再起動する」）で言い切られている
- [ ] 前提条件（環境、権限、事前に必要な作業）が手順の前に書かれている
- [ ] 条件分岐が「〜の場合は△△する」の形で、条件と操作が対応している

### UI文言・エラーメッセージ

- [ ] 文字数が画面の制約内である
- [ ] ユーザーの操作ミスを責める表現になっていない（「不正な入力です」→「入力内容を確認してください」）
- [ ] 次に何をすればよいかが示されている

### 提案書・報告書

- [ ] 出典・根拠が具体的である
- [ ] 推奨・結論が明示されている（ケースバイケースで終えていない）
- [ ] 箇条書きが「**ラベル：**内容」の型で単調に並んでいない
