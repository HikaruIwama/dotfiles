# TDDによる実装

機能追加、不具合修正、振る舞いの変更は、原則としてテストを先に書いて進める。ユーザーの明示的な指示と対象リポジトリの規約を尊重し、既存の言語、テスト構成、実行手順に合わせる。

実装前に[testingスキル](../testing/SKILL.md)を読む。テストの設計、期待値、テスト層、モック、検出力の判断は、その規約に従う。

## 小さな振る舞いごとにRed → Green → Refactorを繰り返す

1. 依頼の受け入れ条件を整理し、次に実装する小さな振る舞いを一つ選ぶ。関連する既存テストと実行手順を確認する。
2. **Red（失敗確認）**：その振る舞いを検証するテストを先に書き、対象テストを実行する。不具合修正では、不具合を再現する回帰テストにする。期待した振る舞いが未実装、または不具合が残っているために失敗したことを確認する。環境不足、テストの誤記、無関係な構文エラーを失敗確認に数えない。必要なら宣言や空の実装だけを用意し、振る舞いを実装する前に失敗を確認する。
3. **Green（最小限の実装）**：そのテストを通すために必要な実装を加え、対象テストを再実行して成功を確認する。後続のケースや将来の拡張を先回りして実装しない。
4. **Refactor（整理）**：テストが通った状態で、必要な重複除去や読みやすさの改善をする。整理した場合は対象テストを再実行し、成功を保つ。
5. 次の振る舞いに進み、同じ手順を繰り返す。完了時は変更の影響範囲とリポジトリの手順に沿って関連テスト、型検査、Lintなどを実行する。

ケースの候補は先に整理してよいが、テストをまとめて書いてから実装をまとめて進めない。最初からテストが通った場合は、対象の振る舞いが既に満たされているか、テストが変更対象を検証していないかを確認する。失敗を作るために正しい既存実装を壊さない。

## 適用範囲と実行できない場合

- 文書や見た目だけの変更は対象外とする。UIの操作や状態遷移の変更は対象に含める。
- 振る舞いを変えないリファクタリングでは、既存テストで変更前後を確認する。検証が不足する場合は、現在の振る舞いを守るテストを先に追加し、成功を確認してから整理する。
- テスト環境がない場合は、既存ツールや言語の標準機能で検証できるか確認する。新しい依存や大きな環境整備が必要なら、その必要性と影響を示して相談する。
- テストを実行できない場合は、理由と代替の確認方法を示す。実行できないテストを失敗確認済み、または成功したと扱わない。
- 実装が既に存在する場合は、失敗確認のためにユーザーの変更を削除したり巻き戻したりしない。変更前の確認ができなければ、その理由を報告する。

完了時は、確認した振る舞い、修正前の失敗と修正後の成功、実行した検証を簡潔に報告する。TDDを適用できなかった範囲や未検証の項目があれば、理由を添える。
