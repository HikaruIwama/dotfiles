# コミットの粒度

コミットを適切な粒度に分割するための基準と具体例。

## 基本原則

1コミット = revertしても他が壊れない最小単位。

## 分割の基準

### revert可能性

1コミットをrevertしたとき、他の機能が壊れない単位にする。

良い例：

- 機能Aの追加
- バグBの修正

悪い例：

- 機能Aの追加 + 機能Aに依存する機能Bの追加（BをrevertするとAが壊れる）

### 変更の種類で分ける

異なる種類の変更は別コミットにする。

- 機能追加（feat）
- バグ修正（fix）
- リファクタリング（refactor）
- ドキュメント更新（docs）
- テスト追加（test）

例：新機能を追加しながら既存コードをリファクタリングした場合

```text
refactor(core): 共通処理をutilsに切り出し
feat(core): utilsを使った新機能を追加
```

### 無関係な変更は分ける

「ついでに直した」は別コミットにする。

悪い例：

```text
feat(auth): ログイン機能を追加 + READMEのtypo修正
```

良い例：

```text
feat(auth): ログイン機能を追加
docs: READMEのtypoを修正
```

## 具体例

### 良い分割

```text
refactor(api): エラーハンドリングを共通化
feat(api): ユーザー作成エンドポイントを追加
test(api): ユーザー作成のテストを追加
docs(api): API仕様書にユーザー作成を追加
```

### 悪い分割

```text
feat(api): ユーザー作成エンドポイントを追加（エラーハンドリングも共通化）
```

↑リファクタリングと機能追加が混ざっている

## 複雑な変更の分割手順

1. `git status --short`と`git diff HEAD`で変更全体を把握する。
2. 変更を論理的な単位にグループ化する。
3. 各グループが独立してrevert可能か確認する。
4. 依存関係がある場合は、依存される側を先にコミットする。
5. 各グループごとにstaging→コミットを繰り返す。

## ファイル移動の扱い

ファイル移動と参照更新は1コミットにまとめる。

```text
refactor(core): utils.tsをsrc/shared/に移動

- src/utils.ts を src/shared/utils.ts に移動
- インポートパスを更新
```

移動だけのコミットと参照更新だけのコミットに分けると、どちらかをrevertしたときにビルドが壊れる。
