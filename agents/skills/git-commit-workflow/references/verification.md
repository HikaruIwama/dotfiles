# コミット前後の確認

コミットを実行する前と後で、意図した変更が正しく記録されているか確認する。

## コミット前の確認

### staging内容の確認

stagingされた変更が意図した範囲か確認する。

```sh
git diff --cached --stat
```

ファイル一覧と変更量を確認。想定外のファイルが含まれていないかチェック。

詳細な差分を見る場合：

```sh
git diff --cached
```

### 無関係な変更が混ざっていないか

- コミットしようとしている機能・修正と無関係な変更が含まれていないか
- 別のバグ修正やtypo修正が混ざっていないか
- デバッグ用のコード（`console.log`など）が残っていないか

混ざっている場合は、該当ファイルをunstageしてから再度stagingする。

```sh
git restore --staged path/to/file.ts
```

### コミットメッセージの確認

- Conventional Commits形式（`type(scope): subject`）に従っているか
- typeが適切か
- subjectが50文字以内か
- subjectが具体的か（「バグ修正」だけになっていないか）
- bodyが必要な場合、whyが書かれているか

## コミット後の確認

### コミット内容の確認

```sh
git show HEAD
```

- コミットメッセージが正しく記録されているか
- 差分が意図した内容か
- 無関係な変更が含まれていないか

### 空白エラーのチェック

```sh
git diff --check
```

行末の空白やタブの混入などをチェック。エラーが出た場合は修正してからamendまたは新しいコミットで対応する。

### コミット履歴の確認

```sh
git log --oneline -5
```

直近のコミットが意図した順序・内容で並んでいるか確認。

## 問題が見つかった場合

### staging内容が間違っている

まだコミットしていない場合：

```sh
git restore --staged path/to/file.ts  # 該当ファイルをunstage
git add <正しいファイル>              # 再度staging
```

### コミットメッセージが間違っている

まだpushしていない場合：

```sh
git commit --amend
```

### コミット内容が間違っている

修正か取り消しかで対応を分ける。`git reset`とforce-pushは、ユーザーが明示的に指示した場合を除き使わない。

**修正する場合**（間違いを見つけて直したい）：

新しいコミットとして追加する。

```sh
git add <修正したファイル>
git commit -m "fix: 修正内容"
```

**取り消す場合**（このコミット自体をなかったことにしたい）：

revertコミットを作成する。取り消すコミットを指定する。

```sh
git revert <commit-hash>
```

例：`git revert abc1234`（コミット`abc1234`を取り消す）
