# タイトルと本文の作り方

タイトル・本文は事前確認で判定した言語で書く。

## タイトル

Conventional Commits形式に準拠する。

```text
type(scope): subject
```

- `type`：必須。`feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`など
- `scope`：任意。変更の範囲
- `subject`：必須。変更内容の要約

PRは複数コミットを含むことが多い。タイトルはPR全体を代表する変更のtypeを選ぶ。複数のtypeが混在する場合は、最も重要な変更（通常は`feat`または`fix`）を選ぶ。

subjectの書き方：

- 50文字以内を目安にする
- 末尾にピリオドや句点を付けない
- 「バグ修正」だけのような曖昧な表現にしない

## 本文を書くときのルール

- 必ず`git diff <base>...HEAD`で実際の差分を読んでから書く。コミットメッセージだけを頼りにしない
- 「何を変えたか」だけでなく「なぜ変えたか」を概要に書く
- 変更内容は差分から具体的に列挙する。「いろいろ修正」などの曖昧な表現にしない
- 動作確認には実際に実行した検証（lint、test、手動確認など）を書く。実行していない項目を書かない
- issueを閉じる場合は本文に`Closes #123`を含める

## リポジトリのPRテンプレ

以下の順に探し、見つかった時点でそれを使う。

1. `.github/pull_request_template.md`
2. `.github/PULL_REQUEST_TEMPLATE.md`
3. `.github/PULL_REQUEST_TEMPLATE/`配下のファイル（複数ある場合は、どれを使うかユーザーに確認する）
4. `docs/pull_request_template.md`
5. リポジトリルートの`pull_request_template.md`

テンプレが見つかった場合：

- テンプレのセクション構成をそのまま使い、各セクションに差分とコミット履歴から得た内容を記入する
- テンプレ内のチェックリストは、実際に確認した項目だけチェックを入れる
- テンプレの言語が事前確認での判定と異なる場合はテンプレを優先する

## デフォルト本文テンプレ

リポジトリのテンプレがない場合は、以下の構成を使う。

```markdown
## 概要

<変更の目的・背景を1〜3文で>

## 変更内容

- <変更点1>
- <変更点2>

## 動作確認

- [ ] <確認した項目1>
- [ ] <確認した項目2>

## 補足

<レビュワーに伝えたい注意点、既知の制限、関連issueなど。なければこのセクションは省略する>
```
