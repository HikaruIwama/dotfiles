# 日本語の文書の書き方

日本語の文書を書くとき、レビューするとき、リライトするときに使う。読み手が一度で意味を取れる文を、文の組み立てから作るのが狙いである。表記や敬語の決め事は、その補足として扱う。

## 文書種別ごとの既定

| 種別 | 文体 | 読み手の指し方 | 特に効く規則 |
| --- | --- | --- | --- |
| 社内開発ドキュメント（README、設計書、ADR、PR・Issue、障害報告） | 既存文書に合わせる。新規文書では読み手と用途に応じて敬体・常体を選ぶ | 「開発者」「担当者」。二人称は使わない | 序盤で要点を示す、事実と推測の分離 |
| 顧客向け文書（提案書、要件定義書、報告書） | 敬体（です・ます調） | 「お客様」「貴社」 | 二重敬語の排除、断定の範囲を根拠に合わせる |
| UI文言・エラーメッセージ | 敬体。体言止め可 | 二人称を避け、操作と結果で書く | 文字数の上限、ユーザーを責めない、次の行動を示す |

手順書の操作指示は、選んだ文体に合わせて「保存する」「保存してください」のように操作を直接示す。本文の文体は不必要に混在させない。常体を選んでも「である」を語尾の定型にせず、内容に合う述語で書く。

## 構成と論証の規則

- 冒頭で目的や要点を伝える。タイトル直下に書いても、「概要」節にまとめてもよい。背景や経緯が長くなる場合も、読み手が結論を探さずに済む位置に置く。
- 一つの段落には一つのトピックだけを置く。段落の最初の文を読めば、その段落が何の話かわかるようにする。
- 見出しには、その節が扱う対象・答える問い・情報の種類を示す。Issueの「概要」「再現手順」のような見出しも、読み手が情報を探す助けになるなら使う。書き手の作業を述べるだけの見出しや、結論を標語のように言い切る見出しは避ける。
- 箇条書きは並列の項目にだけ使う。因果や論証を箇条書きに分解しない。各項目が前提を共有している場合は、箇条書きの前に前提を一文置く。
- 箇条書きの項目数を3つに揃えるために水増ししない。項目数は実際に言いたいことの数で決める。
- 見出しは、話題の切り替わりや、読み手が探す項目の単位で置く。本文の長さだけを基準に増やさない。
- 事実と推測を分離する。原因を推測する場合は、確認できた事実、推測の根拠、未確認の点を区別する。
- 因果を書くときは、何がどの経路や条件で次の事象につながったかを示す。
- 前方参照は、その段落・節の論証が一段落した位置に置く。参照先で実際に回収されていることを確認する。
- 予告（「以下では〜を説明する」）や書き手の振る舞いの宣言（「専門用語は使わずに説明します」）を書かず、内容から始める。文を消しても読み手が困らないなら、予告か宣言である。文書の内容として意味を持つ範囲記述（「本仕様の対象は〜である」、スコープ外の節など）は仕様なので残す。
- 本文で太字を使わない。強調したい内容は、段落の最初の文や見出しに置いて示す。太字を散らすと、要点を文の組み立てで示さずに済ませることになり、読み手には全部が強調に見える。箇条書きの各項目の頭を太字のラベルにする型（「ラベル：内容」）も同じで、ラベルを外して内容を直接書く。用語を定義する箇条書きの見出し語だけは除く。

## 文の組み立て

日本語として不自然な文の多くは、以下の原則のどれかに反している。禁止表現を避けるのではなく、各原則の判定の問いに答えられる文を書く。原則ごとの理由、例、よく現れる形は`references/sentence.md`にある。

| 原則 | 判定の問い |
| --- | --- |
| 一文に一つの事柄を書く | この文の言いたいことを、一つの述語で言えるか |
| 述語に中身を入れる | 述語を読んで、何をするのか、どういう状態なのかがわかるか |
| 確信度は文末で一度だけ示す | 文末の確信度が、書いた根拠に見合っているか |
| 動作主を読み手がたどれるようにする | この文の動作を誰がするのか、読み手が答えられるか |
| 英語の構文を写さない | この文は、日本語で最初から書いても同じ組み立てになるか |
| 長い修飾語を先に置く | 各修飾語がどの語に掛かるか、一度読んで決まるか |
| 文と文の関係を一つ選んで示す | 前の文との関係を一語で言えるか |
| 具体的な動作は具体的な語で書く | この語を読んで、読み手が同じ作業を再現できるか |

表記、敬語、文体の混在のように原則から導けない決め事は、`references/conventions.md`に従う。

## 書くとき

1. 文書種別を判定し、上表の文体方針を確認する。
2. 「構成と論証の規則」のとおりに、冒頭で目的や要点を伝える。
3. 「文の組み立て」の原則に沿って本文を書く。判断に迷ったら`references/sentence.md`の例を見る。
4. 本文のまとまりに応じて見出しを置き、各節の内容と合っているか確認する。
5. 書き終えたら`references/checklist.md`の手順で自己点検する。

## レビュー・リライトするとき

`references/checklist.md`の順に、表記 → 文 → 段落 → 文書全体と粒度を上げながら見る。

指摘は次の3点セットで書く。書き換え案のない指摘は出さない。

1. 該当箇所の引用
2. 何が問題か
3. 書き換え案

### 変更してはいけないもの

- コードブロック、ログ、コマンド出力、設定ファイルの引用
- 引用文、他社・他者の固有名詞、製品名の正式表記
- 意味そのもの。曖昧な箇所は書き換えず、質問として出す
- そのドキュメント群で既に一貫して使われている表記（本スキルの既定と異なっていても既存の表記に合わせる）

## 参照

- `references/sentence.md`：文の組み立ての原則ごとの理由、例、よく現れる形と直し方
- `references/conventions.md`：表記（送り仮名、カタカナ語、数字、記号、和欧間スペース、用語統一表）、文体、敬語の決め事
- `references/checklist.md`：レビューの手順、検査スクリプトの使い方、文書種別ごとの追加チェック
- `scripts/check.py`：表記と、原則に反した形のうち字面や数で拾えるものの機械的な検査
