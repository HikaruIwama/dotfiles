# 日本語の文書の書き方

日本語の文書を書くとき、レビューするとき、リライトするときに使う。読み手が一度読めば意味がわかる文を、文の組み立てから作りたい。表記や敬語の決め事は、その補足として扱う。

## 文書の種類ごとの文体

| 種類 | 文体 | 読み手の呼び方 | 特に気をつけること |
| --- | --- | --- | --- |
| 社内の開発ドキュメント（README、設計書、ADR、PR・Issue、障害報告） | 既存の文書に合わせる。新しく書くなら、読み手と用途で敬体か常体かを選ぶ | 「開発者」「担当者」。二人称は使わない | 最初のほうで要点を伝える、事実と推測を分ける |
| 顧客向けの文書（提案書、要件定義書、報告書） | 敬体（です・ます） | 「お客様」「貴社」 | 二重敬語を使わない、言い切る範囲を根拠に合わせる |
| UI文言、エラーメッセージ | 敬体。体言止めでもいい | 二人称を避け、操作と結果で書く | 文字数の上限、ユーザーを責めない、次にすることを示す |

手順書の操作は、選んだ文体に合わせて「保存する」「保存してください」のようにそのまま書く。一つの文書の中で文体を混ぜない。常体で書くときも「である」を決まった語尾にせず、中身に合う述語で終える。

## 文書の組み立て

- 目的や要点は最初に書く。タイトルのすぐ下でも、「概要」の節でもいい。背景や経緯が長くなっても、読み手が結論を探さなくて済む位置に置く。
- 一つの段落では一つの話題だけを扱う。段落の最初の文を読めば、何の話かわかるようにする。
- 見出しには、その節が扱うものや答える問い、載っている情報の種類を書く。Issueの「概要」「再現手順」のような見出しも、読み手が情報を探しやすくなるなら使う。書き手がしたことを並べただけの見出しや、結論を標語のように言い切る見出しは避ける。
- 見出しは、話題が変わるところや、読み手が探す単位で置く。本文が長いからという理由だけで増やさない。
- 箇条書きは、並んだ項目にだけ使う。因果や論証をばらして箇条書きにしない。項目に共通の前提があるなら、箇条書きの前に一文で書く。
- 箇条書きの項目を3つに揃えようとして水増ししない。項目の数は、言いたいことの数で決まる。
- 事実と推測を分ける。原因を推測するときは、確かめた事実、推測の根拠、まだ確かめていないことを分けて書く。
- 因果を書くときは、何がどんな経路や条件で次のことにつながったのかを書く。
- 後の節を参照する（「詳しくは後述する」）のは、その段落や節の話が一区切りついたところにする。参照先で本当にその話をしているかも確かめる。
- 予告（「以下では〜を説明する」）や、書き手の振る舞いの宣言（「専門用語は使わずに説明します」）を書かず、中身から始める。消しても読み手が困らない文なら、予告か宣言だと思っていい。ただし「本仕様の対象は〜」やスコープ外の節のように、文書の中身として意味のある範囲の説明は仕様なので残す。
- 本文で太字を使わない。強調したいことは、段落の最初の文や見出しに置いて示す。太字を散らすと、要点を文の組み立てで示さずに済ませてしまい、読み手には全部が強調に見える。箇条書きの各項目の頭を太字のラベルにする型（「ラベル：内容」）も同じで、ラベルを外して中身をそのまま書く。用語を定義する箇条書きの見出し語だけは例外にする。

## 文の組み立て

日本語として不自然な文の多くは、次のどれかに反している。禁止表現を覚えて避けるより、それぞれの「見るところ」を満たす文を書くほうが効く。理由や例、よく出る形は`references/sentence.md`にまとめた。

| 組み立て方 | 見るところ |
| --- | --- |
| 一文に一つのことを書く | その文の言いたいことを、一つの述語で言えるか |
| 述語に中身を入れる | 述語を読んで、何をするのか、どんな状態なのかがわかるか |
| 確かさは文末で一度だけ示す | 文末の確かさが、書いた根拠に見合っているか |
| 誰がするのかをたどれるようにする | その動作を誰がするのか、読み手が答えられるか |
| 英語の構文を写さない | 日本語で一から書いても、同じ組み立てになるか |
| 長い修飾語を先に置く | どの修飾語がどの語に掛かるか、一度読んで決まるか |
| 読点は区切りが要るところにだけ打つ | その読点を外して、読み違いが起きるか |
| 前の文とのつながりを一つに決める | 前の文との関係を一言で言えるか |
| 何をするかを具体的な言葉で書く | その言葉を読んで、読み手が同じ作業をできるか |

表記、敬語、文体の混在のように、組み立て方からは決まらないことは`references/conventions.md`に従う。

## 書くとき

1. 文書の種類を決めて、上の表で文体を確かめる。
2. 「文書の組み立て」のとおり、最初に目的や要点を書く。
3. 「文の組み立て」に沿って本文を書く。迷ったら`references/sentence.md`の例を見る。
4. 本文のまとまりに合わせて見出しを置き、節の中身と合っているか確かめる。
5. 書き終えたら`references/checklist.md`の手順で見直す。

## レビュー、リライトするとき

`references/checklist.md`の順に、表記、文、段落、文書全体と、見る範囲を広げながら確かめる。

指摘は次の3つを組にして書く。書き換え案のない指摘は出さない。

1. 該当する箇所の引用
2. 何が問題か
3. 書き換え案

### 変えてはいけないもの

- コードブロック、ログ、コマンドの出力、設定ファイルの引用
- 引用文、他社や他人の固有名詞、製品名の正式な表記
- 意味そのもの。曖昧なところは書き換えずに、質問として出す
- そのドキュメント群でずっと使われている表記（このスキルの決め事と違っていても、既存の表記に合わせる）

## ほかのファイル

- `references/sentence.md`：文の組み立て方ごとの理由、例、よく出る形と直し方
- `references/conventions.md`：表記（送り仮名、カタカナ語、数字、記号、和欧間スペース、用語統一表）、文体、敬語の決め事
- `references/checklist.md`：レビューの手順、検査スクリプトの使い方、文書の種類ごとの確認項目
- `scripts/check.py`：表記と、文の組み立てに反した形のうち、字面や数で拾えるものを機械的に調べる
