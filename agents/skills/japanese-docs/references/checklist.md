# レビューの手順

## 1. 機械的に拾えるもの（先にスクリプトで直す）

人が読む前に、このスキルの`scripts/check.py`にかけて直す。コードブロック、インラインコード、リンク先は調べない（和欧間スペースだけは、インラインコードの前後も見る）。

```sh
python <このスキルのディレクトリ>/scripts/check.py <対象ファイル>...
```

出力は`<ファイル>:<行>:<列>: <分類>（<参照先>）: <ヒットした文字列>`の形で、ヒットがあれば終了コード1を返す。参照先は、スキルのディレクトリからのパスと節の見出しを並べたもの。

調べる単位は3つある。

- 行：表記、記号、太字、用語統一表の「使わない」表記、文の組み立てに反した形のうち字面で拾えるもの（「を行う」「が求められる」「単なる〜ではなく」など）
- 文と段落：100字を超える文、ひらがなの後の読点が3つ以上ある文（漢字やカタカナの後の読点は並列が多いので数えない）、1文の中の推量の重なり、1段落の中のヘッジや文頭の「また」「さらに」の重なり
- 文書：敬体と常体が混ざっていないか（多いほうと違う文体の文を報告する）

ヒットは候補にすぎない。直すかどうかは参照先を読んで決める。特に次の誤検出に気をつける。

- 「事」「為」を含むパターンは、「事件」「事故」「事業」「仕事」「大事」「工事」「行為」「為替」のような語にもヒットする。形式名詞（〜する事、〜た事、〜という事が、〜の為）かどうかを見てから直す。
- 長い文や読点の多い文は、分けると論理が切れるならそのままでいい。
- 文体の混在は、引用や作例の多い文書だと、そちらを多いほうと数えてしまうことがある。

## 2. 表記

- [ ] `references/conventions.md`の各節（カタカナ語の長音とスペース、漢字とひらがなの使い分け、送り仮名、数字、記号、日付・時刻、用語統一表、文体、敬語）に沿っている

## 3. 文

- [ ] 主語と述語が対応している
- [ ] `SKILL.md`の「文の組み立て」の見るところを、全部満たしている
- [ ] 迷ったところは、`references/sentence.md`の例と見比べた
- [ ] `SKILL.md`の「文書の組み立て」のうち、事実と推測を分けること、因果の経路を書くことを満たしている

## 4. 段落

- [ ] `SKILL.md`の「文書の組み立て」のうち、段落と箇条書きの決まりを満たしている
- [ ] 前の段落とのつながりが、接続の言葉か文脈でわかる

## 5. 文書全体

- [ ] `SKILL.md`の「文書の組み立て」にある、最初に要点を書くことや見出し、後の節の参照の決まりを満たしている
- [ ] どの見出しも、その節が扱うものや答える問い、情報の種類を示している
- [ ] `SKILL.md`の「変えてはいけないもの」を変えていない

## 文書の種類ごとの確認

### 障害報告

- [ ] 時系列が起きた順に並んでいる
- [ ] 事実（ログや計測値）と推測が、別の文に分かれている
- [ ] 恒久対応の担当者と期限が書いてある

### ADR、設計書

- [ ] 決めたことが最初にわかる
- [ ] 決めた理由が書いてある
- [ ] 検討して見送った案が、見送った理由と一緒に書いてある

### PRやIssueの説明

- [ ] 変更点が箇条書きか1段落ではっきりわかる
- [ ] 動作の確かめ方が書いてある
- [ ] 影響の範囲（互換性、既存の機能への影響）が書いてある

### 手順書

- [ ] 操作の指示が文書の文体に合っていて、操作をそのまま書いている（「保存する」「保存してください」など）
- [ ] 前提（環境、権限、先に済ませておく作業）が手順の前に書いてある
- [ ] 条件で分かれるところは、条件と操作が対応していて、文書の文体に合っている

### UI文言、エラーメッセージ

- [ ] 文字数が画面に収まる
- [ ] ユーザーの操作ミスを責める言い方になっていない（「不正な入力です」→「入力内容を確認してください」）
- [ ] 次に何をすればいいかが書いてある
