# PR Workflow

PRを作成するときのワークフロー。エージェントが実行する。対話的な操作は使わない。

## 1. baseブランチを決定する

以下の順で決める。

1. ユーザーの指定
2. `git config branch.<current>.gh-merge-base`
3. リポジトリのデフォルトブランチ（`gh repo view --json defaultBranchRef`）

## 2. 前提を確認する

```sh
git fetch origin
git status --short --branch
gh pr list --head <branch>
```

- 現在のブランチがbaseブランチと同じ場合は、作業ブランチを作るかユーザーに確認する。baseブランチのままPRを作らない
- 未コミットの変更がある場合は、PRに含めるかユーザーに確認する。含める場合は`commit`でコミットしてから進む
- 同じブランチから既にPRが作られている場合は新規作成せず、既存PRの更新が必要かユーザーに確認する

## 3. 変更内容を確認する

PRに含まれるコミットと差分を確認する。ローカルのbaseブランチは古い可能性があるため、`origin/<base>`と比較する。

```sh
git log --oneline origin/<base>..HEAD
git diff origin/<base>...HEAD
```

- どのファイルがどう変わったか
- コミットが意味のある単位に分割されているか。不適切な場合はPR作成に進む前にユーザーへ相談する
- デバッグ用コード（`console.log`など）や無関係な変更が混ざっていないか

リポジトリにlintやtestのコマンドがあれば実行する。`package.json`のscripts、`Makefile`、`lefthook.yml`、`.github/workflows/`などから特定する。失敗した場合は修正してから進む。失敗したまま作成する場合はユーザーに理由を確認する。

PRの言語とタイトルの形式は、リポジトリの慣習に従う。以下の直近の履歴で判定する。

```sh
git log --oneline -10 origin/<base>
gh pr list --state all --limit 10
```

- 日本語中心なら日本語、英語中心なら英語で書く。混在している場合は直近の傾向を優先する
- 言語を判定できない場合（新規リポジトリなど）はユーザーに確認する

## 4. タイトル・本文を作成する

`references/title-and-body.md`に従う。

## 5. PRの内容をユーザーに確認する

base・headブランチ、タイトル、本文の全文をまとめて提示し、承認を得る。タイトルや要約だけの提示では不十分。

```text
以下の内容でPRを作成します。

base: main ← head: feat/xxx

タイトル:
feat: ログイン機能を追加

本文:
---
## 概要

...
---

この内容でよいですか？Draftで作成しますか？
```

- 依頼の時点でDraftかどうかの指定がなければ、同時に確認する
- レビュワー・ラベル・アサイニーは、ユーザーから明示的な指示がある場合のみ付与する。推測して提案しない
- 修正要望があれば調整して再度提示する。承認されるまで繰り返す

## 6. pushする

承認後、手順2の`git status --short --branch`の結果に応じてpushする。`gh pr create`のpushプロンプトに任せない。

- リモートブランチがない、またはローカルが先行している（`ahead`のみ）：`git push -u origin <branch>`
- リモートにローカルにないコミットがある（`behind`を含む）：pushせず、取り込み方をユーザーに確認する

## 7. PRを作成する

本文はファイル書き込みツールで、リポジトリ外の一時ディレクトリにファイルとして書き出し、`--body-file`で渡す。作業ツリー内に作ると、未追跡ファイルとして残り後のコミットに紛れ込む。`--body`への直接埋め込みや、シェルのリダイレクト・ヒアドキュメントでのファイル作成は、PowerShellでは文字の解釈や文字コード（5.1の`>`はUTF-16LE）で本文が壊れるため使わない。

```sh
gh pr create --title "<タイトル>" --body-file <本文ファイル> --base <baseブランチ> [オプション]
```

- Draft：`--draft`
- レビュワー：`--reviewer <login>`（複数指定可）
- アサイニー：`--assignee <login>`（自分なら`@me`）
- ラベル：`--label <name>`（複数指定可）

`--fill`は使わない。PowerShellでタイトルに`$`やバッククォートを含む場合はシングルクォートで囲む。タイトルにダブルクォートは使わない。

作成に失敗した場合：

- 「already exists」系のエラー：既存PRがある。新規作成ではなく既存PRの更新が必要かユーザーに相談する
- 認証エラー：`gh auth status`で認証状態を確認し、ユーザーに伝える
- baseブランチが見つからない：指定したbaseが正しいか確認する

作成後、本文ファイルを削除する。

## 8. 検証する

本文が文字化けせず、Markdownのセクション構成が保たれているか確認する。`--jq`で値だけを取り出すと、改行がエスケープされずにそのまま読める。

```sh
gh pr view --json body --jq .body
gh pr checks
```

`gh pr checks`は1回だけ実行し、完了を待たない。失敗しているチェックがあれば原因を調べる。実行中やチェック未登録の場合はその旨を伝える。

最後にPRのURLを提示し、CIの状態や注意点があればあわせて伝える。

## やってはいけないこと

- force-push、baseブランチへの直接push
- `--body`への本文の直接埋め込み
- 承認前のpush、タイトル・本文を提示せずにPRを作成する
- 対話的な`gh pr create`（プロンプトに頼る実行）
- レビュワー・ラベルの推測
